## Why

AgentGuild 当前将 GitHub Issue 的标题和正文直接映射为 Task，无法保证执行 Agent 获得足够的代码上下文、修复路径和可验证的完成标准。要成为开源生态的任务分发中心，平台必须把核心承诺建立在可追溯的分析过程和严格的发布门禁上：不是宣称分析永远正确，而是保证公开任务具有充分证据、明确的不确定性和可客观执行的验收标准。

## What Changes

- 在 Issue 同步与 Task 发布之间增加后台分析 Agent。它按计划获取新建或变更的 Issue，读取仓库结构、相关代码、测试、贡献指南和历史上下文，生成结构化任务分析。
- 任务生成 Agent MUST 使用 Pi Agent Harness（`earendil-works/pi`，原 `badlogic/pi-mono`）执行；平台固定 Pi release/commit、SDK 依赖和容器 digest，并将其纳入不可变 Agent Version 与质量回归。
- 将分析结果固化为版本化任务规格，至少包含问题诊断、证据引用、影响范围、建议修复方案、实施步骤、约束与非目标、风险、验收标准、验证命令及预期结果。
- 增加任务质量门禁。系统检查来源证据、字段完整性、验收标准的可判定性、方案与验收的一致性以及分析置信度；未达门槛、存在关键歧义或无法访问必要代码时，任务 MUST 保持草稿且不得被领取。
- 对不确定分析提供明确处置：记录缺失信息与待澄清问题，支持重新分析和人工复核，不得用未经证实的推断填充正式任务。
- 建立分析和任务规格的完整溯源，包括源 Issue revision、仓库 base commit、分析 Agent Version、模型/工具配置、生成时间、质量检查结果和后续修订历史。
- 将通过质量门禁的任务发布到公共任务池，使第三方 Agent 能发现、领取并提交成果；公共访问只授予单个任务及其仓库交付所需的最小权限，不开放任务所属租户的其它资源。
- 领取任务的 Agent 获得不可变的任务规格快照。Issue 后续变化触发新分析；已领取任务不得被静默改写，重大变化通过取消、替代任务或显式 revision 处理。
- 自动验证和人工评审 MUST 以任务发布时的验收标准为依据，并保存每条标准对应的验证证据，使“完成”成为可审计的判定而不是主观描述。
- 从已接受和已拒绝的执行结果中提取版本化仓库经验；经验必须带来源证据、适用 commit 范围、置信度和冲突状态，经过验证后才能用于后续 Issue 分析。
- 公开仓库共享可由公开 commit 与评审证明的基础经验；租户策略和私有补充保存在隔离覆盖层中，不得进入公共检索结果。

## Capabilities

### New Capabilities

- `issue-analysis`: 后台分析 Agent 获取 Issue 与固定仓库版本的相关上下文，生成带证据、置信度、风险和待澄清问题的版本化分析结果。
- `task-quality-assurance`: 对任务分析与验收标准执行完整性、可判定性、一致性和证据质量检查，只允许达到发布门槛的任务进入可领取状态。
- `public-task-distribution`: 将质量合格的开源任务发布到公共任务池，并允许外部 Agent 在任务级最小权限下发现、领取和提交成果。
- `repository-experience`: 从任务执行、验证和评审结果中提取、验证、版本化并检索仓库级经验，形成公共基础经验与租户私有覆盖层。

### Modified Capabilities

- `task-lifecycle`: Issue 来源任务先以 draft 保存，只有通过质量门禁才能进入 open；领取后绑定不可变任务规格版本，源 Issue 变化不得静默修改执行契约。
- `task-mcp-access`: 任务发现、领取和读取接口需要向执行 Agent 提供完整的结构化任务规格、验收标准版本及必要证据引用。
- `agent-access-control`: 在保持租户数据默认隔离的前提下，为公共任务定义显式、任务级、短期且最小化的跨租户访问边界。
- `code-review`: 自动验证和人工评审需要逐条关联任务验收标准及验证证据，并基于领取时的任务规格版本作出结论。

## Impact

- **同步与后台任务**：扩展 `backend/internal/sync`，将直接 Issue→Task 映射改为可重试的获取、分析、质量检查和发布流水线；需要独立的分析 job、lease、退避和失败状态。
- **任务领域与存储**：扩展 Task 内容模型和状态转换，新增分析记录、任务规格版本、证据引用、质量报告、验收标准及 Issue/base commit 快照；需要数据库迁移和历史数据兼容策略。
- **Agent 集成**：新增隔离的 Pi SDK runner 与 Go provider adapter；分析 Agent 必须以不可变 Agent Version 运行并记录 Pi release/commit、容器 digest、extension hash、模型、Prompt、Skill 和工具配置；仓库与 Issue 内容按不可信输入处理。
- **API 与 MCP**：新增分析状态、质量报告、重新分析/复核、公共任务发现和结构化任务规格读取能力；现有 claim、submission 和 review 契约需携带 task specification version。
- **Git 与验证**：分析阶段需要固定 base commit 的只读仓库上下文；验证阶段按验收标准执行允许的确定性检查，并保留命令、环境和结果证据。
- **仓库经验**：新增经验候选、证据、版本、适用范围、冲突和撤销模型；后续分析记录实际使用的经验版本，支持效果评估和回滚。
- **前端**：同步规则页增加分析策略和质量门槛；任务详情展示问题诊断、方案、证据、验收标准及置信度；治理界面展示草稿、待澄清、质量失败、待复核和已发布状态。
- **安全与运营**：公共任务分发引入跨租户任务级授权、滥用控制、成本限制、Prompt Injection 防护、分析可观测性和审计要求。
- **兼容性**：普通 Agent 发布的任务保持现有流程；Issue 同步任务从直接发布改为先分析后发布，属于有意的行为变化。
